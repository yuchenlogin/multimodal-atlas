# Technical-report 改造方案（动笔前）

日期：2026-10-16；对象：全部 13 篇报告及其网页、PDF、阅读入口。

## 诊断与借鉴范围

旧稿反复采用“谱系—代表论文—前沿—机会”的综述模板，缺少贯通公式、实现与证据的技术问题。此次不以篇幅、模型数量或增加引用条目作为完成标准。旧稿保留在 Git 历史，原有未复核文献不继续以“全部核验”的名义背书。

参考 CS336 官方课程与 executable lectures，重点审读 resource accounting、evaluation、data、policy-gradient training walkthrough。借鉴其先暴露问题、明确定义与计算、检查实现、再设计实验的顺序；不是复制课程文字，也不把多模态内容改成课程摘要。

## 写作与图表约束

- 每篇围绕具体任务建立记号与假设，至少展开一个推导/算法和一个有数值的工作示例；解释关键设计的替代方案与适用条件。
- 方法图画出输入、输出、损失或控制信号；结果图必须注明数据来自原论文、本文实际运行的教学实验，还是由假设直接算出的预算曲线。不得把后两者称作模型复现。
- 每个引用结果记录论文版本、表/图/章节、任务、数据、模型与评估条件；跨设置的点不能连成因果提升曲线。
- 用少量核心论文支撑深入讨论，删去泛化宣传、无证据的 SOTA、对未来的确定性判断与批量模板化评级。
- 保存数据 CSV/JSON、可复现绘图与教学实验脚本；网页与 PDF 共用同一份 Markdown。

## 工作顺序与验收

1. 保存原稿审计；核验核心来源，先建立 evidence ledger，再写结果段。
2. 重写全部 13 篇，补方法图、定量图、实现细节、失败案例和实验协议。
3. 运行教学实验，重建图、HTML、PDF，验证公式、图片、链接、长表和移动端。
4. 成稿后开启三个不同身份的 sub-agents：研究方法与证据审稿人、研究生读者/教学编辑、系统实现与可复现性审稿人；按问题修订，再复核。代码改动另按 adversarial-review skill 调用 CLI reviewers。
5. 必须解决所有经确认的 high/medium 问题；争议问题记录证据与取舍，不以 reviewer 简单说“满意”替代验收。
6. 更新 CHANGELOG，提交 GitHub PR。用户本轮要求提交 GitHub；不沿用上轮对 PR #1 的合并授权来自动合并新的内容改造。
